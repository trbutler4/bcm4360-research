# OpenBRCM default-branch audit

Audit date: 2026-10-02. Default branch pin: `06d60d610f4e1cba1f20a188453c8f3ba69357fb`. The newer unmerged branch `22e77166f73c39dbf3d827c949403fda26e93bc8` is being audited separately. None of these results are a real-radio reproduction.

## What the default branch does

OpenBRCM is a from-scratch `bcma`/`mac80211` SoftMAC project targeting BCM4352 PCI `14e4:43b1`, not a tested BCM4360 MacBook driver. Its architecture delegates MLME, crypto, scheduling and regulatory policy to Linux rather than reconstructing the whole proprietary station stack. This is sound scope reduction, but its self-imposed rule against copying even GPL-compatible in-tree driver code imposes additional implementation work.

The advertised hardware milestones are sharply scoped: validated firmware acquisition, D11 ucode upload/PSM start, exactly 610 common initvals, an isolated DMA lifecycle with no TX payload mappings and 64 RX buffers, and a vendor-ordered pre-PHY D11 tail. Author-published runtime logs include artifact commit/hash identities and verified DMA stop/release. They explicitly do not prove PHY/radio/channel/calibration, completed RX frames, scan, association or data traffic.

Primary sources, all relative to the default-branch pin:

- `README.md:1-59`: status, BCM4352 target, default-branch band-init analysis only.
- `src/ob_mac80211.c:100-155`: start and channel configuration return `-EOPNOTSUPP`; TX frees the skb and logs that it is unimplemented.
- `src/ob_mac80211.c:70-95,223-242`: HT 2x2 capabilities are advertised as silicon capability, not evidence of working HT packet processing. 5 GHz is not exposed.

## Provenance and reproduction

`docs/provenance.md:6-26` says implementation derives from a separate RE specification generated by analysis of a pinned proprietary object, and forbids copying other kernel drivers. The implementation is tagged GPL-2.0-only. This is a disclosed policy, not independent legal clearance.

`docs/re-tooling.md:11-29,79-94,129-145` depends on the maintainer's external local Rust tool workspace, persistent index and separate specification. These tools are not supplied by this public checkout. The author's public GitHub repository list was checked and does not expose a clearly corresponding RE/spec tool repository. It may exist elsewhere, so the conclusion is only that a public reconstruction recipe is not provided here.

`docs/firmware.md:7-39` separates vendor images from the host code, with strict sizes and FNV-1a hashes. Its 8-byte little-endian initval records are not interchangeable with b43's on-disk firmware format. A name such as `bcm43xx-ucode.fw` is a fallback for an exact pinned image, not permission to substitute arbitrary brcmsmac firmware.

The user's existing Nix vendor archive yielded an object SHA256 `352a6e349f74c69b78e76f68c63752c99b8f6b22dc942af531b754211d7f4743`, exactly the project pin. A temporary Nix environment supplied pyelftools0.32. No object was linked into a module or loaded.

## Reproduced safe tests

1. `make hosttest`: exit0. Ten C host suites pass, 19 SPROM-decoder Python tests pass. Seven vendor-table tests initially skip because the object/parser dependency is missing. Optional installed-firmware checks skip because the exact images are not in `/lib/firmware`. GCC15.3 reports `-Wmaybe-uninitialized` warnings in the optional real-file test's stats accesses. No warning or pass is misrepresented as hardware validation.
2. `make -B hosttest CFLAGS='-O1 -g -Wall -Wextra -I. -I../../src -fsanitize=address,undefined -fno-omit-frame-pointer'`: exit0 for the same host subset, no sanitizer findings on exercised cases. Same optional-input limits.
3. `OPENBRCM_RE_BLOB=<already-extracted-object> python3 tests/host/test_srom_var_table.py`, in temporary pyelftools environment: **7/7 pass, none skipped**. These independently reproduce table identity/shape, 573 descriptor entries, revision11 field offsets, continuation pairs, absent-value semantics, MAC revision gating, synthesis and bad-source-hash rejection. This validates binary table decoding, not actual board calibration or RF correctness.
4. `sh scripts/docs-check.sh`: exit0, all documented consistency guards pass. These are source/text invariants and claim-scope checks, not proof that author hardware claims are true.
5. A separate local ELF probe extracted all three actual pinned firmware symbols, independently checked complete source SHA256, individual FNV hashes, sizes, terminators and record counts, then a C probe included the original `ob_fw.h` parser under AddressSanitizer/UBSan. All three images pass, changed bytes fail identity, and truncated/extended initval tables fail parsing. This closes the earlier real-image data-validation gap without installing images into `/lib/firmware`. It does not exercise `request_firmware`, module upload, D11 execution or radio hardware. Scripts and logs are `verify_vendor_firmware.py`, `verify_openbrcm_firmware.c`, `vendor-firmware-slices.json`, `openbrcm-real-firmware-probe.log`.

## Useful lessons for the combined project

- Make each bring-up stage have a bounded, evidence-backed stop boundary and distinguish software checks from actual hardware proof.
- Treat DMA engine stop verification and buffer lifetime as hard safety invariants. Core containment alone is not evidence the device can no longer access freed buffers.
- Record exact source, module and firmware identities per experiment.
- Do not infer actual packet capability from `iw phy` registration or HT-capability bits.
- Reuse proven b43/BCMA/mac80211 facilities where licensing and source provenance permit, rather than expanding a new driver solely for purity.
- The public specification/tooling availability needs improvement if external contributors are to independently verify findings.
